# 自动纠察与发布门禁（2D / A 方向）

本规范供独立的 2D 自动开发任务、GitHub Actions、人工验收统一判断。**自检不等于自动自夸**：必须把结论与可复现证据绑定。测试不覆盖的事实标 `unverified`，不得假设 `pass`。

## 问题等级

- **P0（立即阻断）**：页面打不开、运行时异常/数据丢失、旧 2D/3D 存档损坏、无法移动/攻击、生成不可达地牢、资源明显侵犯许可、发布失败。
- **P1（不得称为最终交付）**：未采用 A 向写实 2.5D、场景只是染色、角色仍卡通像素、地图无支路/回路、Boss 强制自动重置、Boss 无专属掉落、怪物只有增血量/换皮、手机触屏重要按钮无法使用、未提交真实可复核截图。
- **P2（应在最终验收前清零或明确批准例外）**：部分微小 UI 溢出、战斗数值波动、低价值装饰不一致、局部短时性能抖动。

发现 P0/P1 必须开缺陷记录，标明复现种子、设备/视口、期望、实际、回归测试 ID、引入的提交及修复 PR。**不能跳过失败门禁继续将阶段标 done**。

## 阶段门禁

| 门禁 ID | 要回答的验证问题 | 必须给的证据 |
| --- | --- | --- |

| G02 | 世界不是自动结算关卡吗？ | 主城→地牢→Boss→继续探索/回城/下一层/手动回刷的状态机集成测试及浏览器录像/截图 |
| G03 | 怪物行为不是换皮吗？ | 6 职责 AI 行为测试，前摇时序、不同战斗组合的录像或真实截图 |
| G04 | Boss 真正值得刷吗？ | 3 专属掉落池、首杀与重复击杀统计、上千次固定种子模拟、不可重复领同一次奖励的测试 |
| G05 | 写实斜俯视地图达到视觉参考了吗？ | 主城、野外、迷宫及 Boss 房同构图实机截图、可追溯材质/贴图授权表、前中后景与碰撞测试 |
| G06 | 人物、怪物和外观同一世界观吗？ | 统一比例/视角的动作片段、6 怪与 3 Boss 资产清单、四装备位前后实际换装截图 |
| G07 | 装备、技能和纸娃娃真实工作吗？ | 13 槽/词缀/套装/战斗伤害/完整技能树数据测试、PC 背包截图与手机交互测试 |

| G10 | 用户确认最终效果且真实线上发布吗？ | 用户对最终实际游戏截图/可玩候选的明确确认、主分支 SHA、Pages workflow success 以及回滚记录 |

## 测试分层

- T0：静态校验（语法、JSON、路径、授权清单、可访问资源）。
- T1：纯规则测试（地图连通性、多种随机种子、怪物状态机、掉落 RNG、装备词缀、存档迁移）。
- T2：浏览器测试（PC/竖屏/横屏，键鼠/触摸、菜单、主城、Boss→不自动重置）。
- T3：真实浏览器画面（与用户参考图并排；固定种子/时间/装备/视口；记录源和提交 SHA，**不以概念图冒充截图**）。
- T4：真实设备和完整长局（只在实际完成时标通过，自动浏览器模拟不可替代）。
- T5：发布核验（Pages 工作流、加载、回滚、旧存档对比）。远程网页无法访问时须如实标记 `unverified`。

## 纠察循环（每次自动运行）

`Inspect → Select → Implement → Test → Visual-review → Defect-triage → Fix → Retest → Evidence → Promote-or-hold`

- **第一检查**：对照用户提交的 5 张目标参考图，自问“这是否还是过去卡通像素角色、单场地、换皮怪？”；是则视觉门禁失败。
- **第二检查**：构建反例：同一地图 100 个固定随机种子、重复通关/死亡/换区/重载、满包拾取、Boss 双重伤害帧，尽可能用自动测试覆盖。
- **第三检查**：运行真实 Chromium 桌面、手机竖屏、横屏；强制保存画面来源/截图 SHA。至少找出最大三项差距；差距没有缩小时不允许只因单元测试绿灯推进。
- **第四检查**：对于发现的问题当轮优先复现并修复；不能解决则保存到 `state.json` 的 defects、工单/PR，下一轮第一任务先修它。
- **第五检查**：使用 `node scripts/audit-2d-final.mjs` 校验路线图状态自身，确保“done”阶段必须拥有门禁证据，没有验收就不得显示“完成”。

## 状态记录

`docs/2d-final/state.json` 为唯一 2D 最终版机读里程碑状态（不要使用 3D 正在写入的 `docs/project-state.json`）。每轮写入前刷新仓库并核对分支 HEAD；当同时存在其他 2D 自动运行/PR 时，以单一任务领取/租约协同，遇冲突退出并在下一轮重试。

状态要含当前阶段、每阶段 pending/active/blocked/done、每次 commit/CI 的真实证据、最大三差距、P0/P1 未解问题、下一可执行动作、候选版本与用户最终批准状态。基线可以通过**元数据结构自检**，但不得因结构正确而自动把阶段标 done。

## 何时通知用户

日常单元测试、增量工作提交只记仓库，不以聊天刷屏。出现需用户付费/授权/许可决策的阻断，或最终可玩的候选已满足所有自动技术与视觉预筛选要求时，才发一条简洁说明并请用户一次性验收。用户没确认之前状态停在 `candidate-review`，**不能暗示用户已经验收通过**。

## 完成与停止

F9 的 `done` 必须有 `G10=pass`、用户明确验收记录和真实部署记录。最终版完成后停止 Diablo 2D 专属自动任务，避免无限反复优化；3D 的另一任务不受影响。
