# VORAGH 2D — A 向最终交付路线图（滚动规划）

> **2026-10-14 不可覆盖的双轨规定：** 当前 Demo 允许参考用户提供的高精致像素法师进行角色和跑步/施法动效试验；最终成品仍锁定用户确认的写实暗黑 A 方向 2.5D，严禁把 Demo 像素角色当作正式版 F4/F5 美术验收通过。详见 [双轨美术纲领](DUAL-ART-DIRECTION.md)。

**唯一视觉目标**：用户确认的写实暗黑、斜俯视 2.5D 参考组图。**这是成品验收标准，不是现有资产描述**。视觉设计必须落到浏览器实际可执行的地图、人物、怪物、装备、UI 素材中，概念图不算实机。

**项目仓库** `TempleHao/Diablo`。现有 `dist/2d/` v0.3 是技术原型；现有 `dist/` 的 3D 版由另一条开发流维护。新 2D 正式版先在独立开发分支完成，禁止覆盖 3D 分支/存档/模型。最终版发布之前保留原版作为可回退基线。除非基于真实验证，不得声称已经达到参考图品质。

## 为什么重构

用户先后发现：当前贴图偏低像素卡通；地图是单场地清怪而不是可探索迷宫；怪物职责单调；Boss 无专属回刷动机；击杀 Boss 强制结算并自动重置；主城、野外、剧情、真实装备外观与双端高品质 UI 缺失。**这些均属交付阻断问题，优先于小规模色调/光效调节**。

## 产品原则与最终用户体验

- **世界结构**：主菜单 → 可反复返回的主城（商人/铁匠/仓库/传送点/任务） → 野外入口 → 程序化多房间地牢 → 精英与事件/宝箱 → Boss 房。允许玩家完成 Boss 后继续探索本层、手动回城、前往下一层或自选重刷；不强制重开。
- **探索**：种子确定、布局可达、支路/死路/回路真实存在、迷雾揭示、可看清房间边界，传送点和解锁状态受存档管理。Boss 不以“消灭 12 怪”自动触发，需玩家自己探索到 Boss 房。
- **战斗**：至少 6 个有独立行为/剪影的普通怪族，支援/远程/近战/追击/冲锋/召唤与至少 4 个精英词缀，攻击有识别前摇、可闪避窗口。Boss 有专属场地和两阶段以上变化。
- **掉落**：至少 3 个 Boss 或区域首领的可区分专属掉落池、首杀保障、重复击杀概率与防重复结算。胜利不会强制离开；战利品有图标、落地可见性、词缀对比和目标刷取路径。
- **成长**：保留且回归现有 13 槽装备、5 种品质、词缀、套装、技能和等级。武器/头盔/胸甲/肩部至少 4 个装备变化真实渲染到角色外观（而非仅文本属性）。
- **视觉**：斜视比例统一的原创或合规授权写实预渲染精灵。主城、野外、监牢、仪式厅、洞穴、首领圣所有实际不同地板/建筑立面/装饰，而非同地图重新染色。夜色、环境冷光与火盆暖光需保证可读性。
- **平台**：PC 浏览器键鼠、手机触摸支持；首期强制测试手机竖屏与横屏布局，技能/摇杆区域不卡关键场景。GitHub Pages 静态优先，无付费服务器默认依赖。

## 开发阶段（按依赖，非日历强制完工）

阶段不代表固定一轮自动任务能做完。每轮只领取一个具体可测子任务，直到对应门禁全过才推进下一阶段；如果当前阶段有阻断问题，必须优先修复。

## 每轮执行协议（自纠察）

1. 读取本路线图、`QUALITY-GATES.md`、`state.json`、主分支和进行中 2D PR、最近 CI 和用户最新反馈；3D `docs/project-state.json` 是**另一个工作流**，只读不得占用或覆盖其租约。
2. 领取一个尚未完成的任务，读取上次失败记录，不重复已验证工作。开发独立分支；如同目录已有工作中的 PR，先判断能否续做，不要制造重复 PR。
3. 编写可运行代码/素材/测试；完成一个小提交就保存 SHA，至少一项机器可重演证据。素材标明来源、许可、可再分发性；不得购买付费资源或违规使用其他商业游戏资产。
4. **执行→自检→反向审查**：单元/集成/浏览器 + PC 与手机视口实机截图；检查色彩明度、世界空间、战斗可读性、词缀真实作用、Boss 流程，并明确列出“与参考图的最大三个差距”。
5. 分类记录 P0/P1/P2，失败先修复并复跑；CI 通过只能证明技术正确，不能证明美术通过。画质差、迷宫假的、掉落鸡肋等均视为 P1 不允许冒充阶段完成。
6. 状态中记录任务 ID、源代码提交、真实测试链接、截图文件、尚未满足的门禁和下次 **具体的代码动作**。工具不可用也要留真实错误，不得凭空宣称完成。
7. 对于未通过关键门禁的修改，PR 保留 draft 不合并；仅当该候选版本同时通过安全、存档、玩法与该阶段视觉门禁才可发布到主分支。最终作品须先达到 F8，再向用户索取 **一次** 最终验收；不要求用户每天指挥。
8. 用户只接收重大阻断、可验收候选与最终成果通知；成功的日常小改动存 GitHub 而不反复打扰。完成 F9 后停止本 2D 定时任务，防止无限优化。

## 可并行但不互相干扰

3D 的 `ART-02` 持有独立租约与已存在任务。2D 开发必须仅修改 `dist/2d/`、`tests/2d-*`、`docs/2d-final/` 等约定范围，避免主分支上与 3D 开发抢锁；涉及公用根文件时走 PR 人工比对，不强行推送。当前 2D 光照 PR #4 为独立可恢复候选，不等于写实美术完成。

## 计划时间口径

按每 5 小时**尝试**执行，不能保证每次都可写入代码；F4/F5 的商业级美术生产需要明显多于单轮脚本修改的工时，若授权资产或运行环境阻断，应记录和升级问题，而不是靠更长时间自动执行保证成品。每阶段的验收日期由实际证据驱动，不编造 ETA。

## 唯一宣称完成的条件

`state.json` 所有阶段 done，F8 所有发布阻断项 pass，F9 人工确认与部署证据完整，并且用户确认当前实机视觉接近所提供的五张参考图。未达到的状态只能称为“开发中”“待验收”“被阻断”，不能称为已最终交付。
