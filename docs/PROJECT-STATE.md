## 每次怎样续做

1. 读取状态文件、队列、根目录AGENTS和最近提交；检查上轮分支、部署失败及实际验证结果。
2. `status=paused/complete` 时停止；有有效租约时不重复开工。无租约或租约已过期时，按AGENTS中的条件提交协议领取。
3. 恢复中断工作包；否则选择最早未完成、依赖已满足的一项。每次只处理一个工作包。
4. 完成小步骤就把改动和断点保存到GitHub。尚未验证的代码放checkpoint分支，记录恢复分支/提交；没有原环境时可从该分支重建。
5. 做改动对应验证，通过后集成main并核验Pages。记录实际完成和失败，不把工具调用成功等同于功能正确。
6. 更新状态和队列，释放自己的租约，简短报告结果。中断时保留最近可靠断点；下一轮从该处恢复。

## 定时与额度的真实边界

定时任务配置为每5小时尝试续做，不是Codex内部额度监听。当前没有可调用的额度查询或自动续额接口，5小时是用户指定的重试间隔。达到该时间不能证明额度已恢复，其他限额也可能继续阻止运行。

任务能否开工还取决于当轮执行工具、GitHub连接与环境是否可用。GitHub连接已在设置前成功读取；未来若断开，应记录实际原因，不能宣称代码已执行。运行若被额度直接终止，可能来不及写最后一行日志，所以保存频率必须以小步骤为单位，不能只在任务末尾保存。

不能用长期sleep、GitHub Actions空等、后台终端或再套一层定时器保证唤醒模型。这些不改变平台额度。本项目也不自动购买额度、创建付费后端或开启未来在线服务。

## 状态文件字段约定

`status`为ready/running/blocked/paused/complete；`nextTaskId`指向队列；`activeRun`保存租约或null；`resumeBranch/resumeCommit/nextAction`定位中断步骤；`lastAttempt`记录真实结果；`blocked`记录已观察原因。`lastCompletedWorkCommit`仅标已验证工作的提交，不标尚未核验的候选。

一个任务的done需要交付、验证、必要的迁移与部署都达到该任务要求。保存了部分代码应标in_progress；工具或额度阻止开工应标blocked；没有任何新结果时不制造更新记录。完成D3并验收后设置complete并暂停本项目定时任务；D4另立范围和服务预算。
