# D1-01 运行边界与存档基线

本工作包保护0.2.0可玩行为和旧档，建立后续拆分边界。三元素构筑、六/十装备位、任务、契约、完整房间恢复和可信在线经济尚未实现；策划字段不能直接当作当前运行字段。下一工作包见[WORK-QUEUE.md](WORK-QUEUE.md)，跨运行开发断点见[PROJECT-STATE.md](PROJECT-STATE.md)。

## 现有模块与职责

| 模块／状态 | 当前职责 | 边界与下一步 |
|---|---|---|
| `dist/game.js` | 启动WebGL、DOM与输入、主循环、相机、HUD、暂停及各模块连接；暂时还包含战斗和物品规则 | 是当前编排入口，并非已经分层的引擎。业务动作通知存档管理器，UI只显示真实结果；后续逐步抽纯规则，不在D1-01重写战斗。 |
| `dist/hero.js` | `loadMage(parent)`加载GLB；返回`model`、`clips`、`update(dt,moving)`、`cast()`和`preview(canvas)`，后者返回关闭预览的清理函数 | 模型与动画表现不拥有经验、装备、伤害或存档。动画播放不算命中；模型加载失败不重置成长。 |
| `dist/environment.js` | `createEnvironment(scene)`返回`group`、`obstacles`、`walkable(x,z)`、`update(dt,time,playerPosition)`；构造固定地窟、圆形障碍与装饰 | 提供可走区域和表现，不生成角色资产。内部固定种子只用于场景装饰，不是关卡／敌群／掉落共同的可恢复随机流。 |
| 战斗运行状态，暂在`game.js` | `running`、`dead`、生命、法力、冷却、位置、敌人、投射物、特效、地面掉落与本轮计数 | 仅内存有效。`reset()`新开一轮，不恢复之前房间；Three.js对象不进入存档。当前`damage()`同时处理表现、成长和保存，尚未解耦。 |
| 角色与物品，暂在`game.js` | `data={level,xp,items,equipped,clears}`；一件法杖增加伤害，库存上限60件 | `items`是已拾取物品，地面`drops`不是库存；`equipped`引用库存ID。换装／分解仍由现有规则负责，不假装已有六槽、词条或制作系统。 |
| `dist/save.js`，D1-01边界 | 接受纯数据，校验、包装版本、读取、迁移、备份、导出与导入；持久化失败返回明确结果 | 不引用DOM、Three.js或修改战斗对象。读取／导入成功后，`game.js`再采用返回数据；失败不得把默认角色写回覆盖旧档。 |

运行顺序是输入意图→现有战斗／物品动作→内存成长数据→请求保存；HUD和渲染读取运行状态。只有存储操作确认成功才显示已保存。失败后内存中本轮成长与磁盘好档可能不同，界面必须保留“未保存”的事实，不能把一次通知消失当作存储已恢复。UI通过管理器操作，不另写localStorage；`previewBackup()`提供恢复候选，`exportStoredSave()`按来源导出持久化原文，它可能是未知版本，不能称为已经验证的可导入备份。

## 存档管理器接入

`save.js`导出`SAVE_KEYS`与`createSaveManager({storage,now})`；可注入存储和时钟进行Node故障测试。管理器方法为同步调用，调用方先`load()`，再允许保存、导入或恢复；以实际返回结果更新角色与状态提示，不凭按钮点击就宣称成功。

| API | 调用职责 |
|---|---|
| `load()`／`getStatus()` | 初始化存档来源、读取角色及保护状态；UI显示迁移、恢复、损坏或存储不可用的实际结果。 |
| `save(data)` | 保存合法成长，保留自动快照；只由已发生的成长／物品变更请求，不每帧写入。 |
| `previewImport(raw)`／`importSave(raw,previousCharacter=null)` | 先展示合法候选，再由明确确认提交整份替换；UI传入实际暂停角色，连同尚未保存的成长建立恢复点；预览不写存储。 |
| `previewBackup()`／`recoverBackup(previousCharacter=null)` | 展示手动恢复点优先的有效候选，确认后恢复；UI传入实际暂停角色使其未保存成长可逆，失败不更换当前角色。 |
| `exportSave(data)` | 序列化合法角色供导出；如来自未保存内存，UI须注明。 |
| `exportStoredSave('primary')`／`exportStoredSave('rejected')` | 导出原始主档或被拒绝来源供备份／排错，不将未知未来格式降级改写；导出不写存储。 |

固定键：`main=ember-mage-save-v2`、`backup=ember-mage-save-v2-backup`、`restorePoint=ember-mage-save-v2-restore-point`、`rejected=ember-mage-save-v2-rejected`、`legacy=ember-mage-v1`。键名不代表完整事务保证，包装中的格式版本与修订才负责兼容和冲突诊断。

## 旧档兼容与恢复范围

旧键为`ember-mage-v1`，值是裸JSON对象，没有`schemaVersion`。迁移保留原键作为兼容来源，不删除它、不持续双写；新格式及键名以`save.js`常量为准。新档存在但无效时不得当作“新玩家”自动覆盖，也不得偷偷退回更旧的角色而声称恢复成功。

- 旧等级合法范围是1–100整数；D1-01不按完整策划的60级截断。100级后旧代码仍累计经验，不能统一要求`xp<level*50`。
- 经验保留有限非负数值，通关次数为非负安全整数；库存ID唯一，名称为字符串，品质为0／1／2，伤害为有限非负数；装备引用为`null`或现有物品ID。校验应先完成，不能静默过滤、截短库存再覆盖来源档。
- [tests/fixtures/legacy-v0.2.0.json](../tests/fixtures/legacy-v0.2.0.json)是按真实结构构造的回归样本，不是用户真实档案：7级、123经验、3次通关、两件法杖，装备31伤害的一件。现有公式应得法术伤害77、最大生命184；ID、品质与装备引用迁移后保持。

导入先解析和完整校验，再备份当前好档并提交替换；无效JSON、未知版本、重复ID或悬空装备引用不得改变当前存档。UI向导入／恢复传入`getData()`所返回的暂停角色，保存失败后的经验、已拾装备和装备选择也进入恢复点，不只保护更旧的落盘角色。成功导入是整份替换，不合并两份库存。导出是成长备份，不包含战斗快照；最后持久化存档与另行导出的未保存内存必须明确区分。

备份分两类：自动保存备份保留最近可靠快照，手动导入／恢复的独立`restore-point`保留被替换的角色；普通保存不能覆盖后者。UI主动恢复优先展示`restore-point`；坏主档启动时优先采用自动保存备份作为候选，并明确提示来源，不假装主档完好。

坏主档或未来格式主档触发写保护，`canSave`与`canImport`独立：仍允许预览有效外部备份并明确确认替换，待导入文件本身是未来格式则拒绝。已知跨页冲突或存储不可读时不允许导入；加载读取失败后必须重新成功`load()`才能恢复写入，故障暂时消失不自动解除保护。显式恢复／替换前先保存原始`rejected`副本，保存失败就不替换，不能通过默认角色自动解除保护。备份无效、空间不足、任一备份或主档写入失败均不得显示成功；失败不得破坏已有来源数据。多个localStorage键不具备完整跨键原子事务。死亡仍保留已拾取成长；刷新只延续已保存成长，本轮敌群、位置与地面掉落重新开始。

本机数据可被玩家修改；格式校验只检查可用性，不证明来源可信。当前跨页保护只乐观检查已知修订并拒绝可观察到的旧页写入，读后写之间仍可能竞争，不能称为跨页原子提交。IndexedDB完整事务、领取幂等日志、跨页写锁、房间快照、风险批次与服务器权威均留在后续工作包，不能以版本包装或备份宣称已经实现。

## D1-02 数据注册接入约束

下一步先提取已实现技能、角色计算和法杖定义为有稳定ID、版本与合法参数的纯数据，行为只映射到代码中的有限处理器。注册表不执行任意字符串代码，不在尚无处理器时显示“已生效”的词条。伤害计算应能脱离DOM与Three.js重算，表现层只消费结果；物品变更提交角色纯数据，存档不反向调用战斗。

新增字段须附默认值、旧档迁移和失败策略，禁止把GLB对象、函数、计时器、DOM节点写进JSON。D1-01保持当前单法杖结构；多装备槽和物品事务按照队列单独验收，后续再扩展格式版本。

## 可复现验证

从仓库根目录运行`npm run dev`，浏览器打开`http://localhost:5173`；`npm run check`检查JavaScript和资产。存档单元验证使用注入的内存存储与故障存储，不读写开发者的真实浏览器档。

最低回归包括：裸旧档迁移后五字段与法杖ID保留；刷新仍能读取；新格式导出／导入往返；坏导入不覆盖好档；备份与主档分别写入失败时原好档不丢；未知新版本不自动覆盖；合法100级高经验不被截断。浏览器再检查保存状态、导入确认、备份恢复和错误文案，不能用单元测试代替WebGL运行或真机性能验证。

2026-10-12，本机执行`npm run check`通过：五个JavaScript文件的语法、GLB模型／蒙皮／动画资源和61项存档测试均通过。用例包含坏旧档外部修复、三个辅助键读取失败后须重新加载、损坏恢复点先归档再修复，以及保存失败后的内存角色经导入／恢复仍可找回。该结果不包含浏览器交互或真机性能结论。

## ART-02 双资产与人物查看

`hero.js`启动只加载战斗L1，成长与保存字段保持不变。近景L0由人物查看首次请求；成功结果与进行中的请求分别缓存，失败清理请求供重试，不预加载近景。LOD两份资产骨架顺序和动作采样一致，但当前按用途选择，没有声称实现屏幕占比动态LOD。

`mage-preview.js`每个canvas保留一个renderer、scene、人物克隆和context。关闭停止RAF、输入监听和resize观察；再开复用已上传资源。高模响应只允许当前visible session采用，关闭期间解析完成只存CPU缓存，不能建新预览或恢复游戏。初始化失败仍可关闭；GPU/内存保留是显式取舍：本页只保留一个查看上下文，不声称关闭释放GPU内存。未来低内存策略与真机测试另行验证。

替换克隆只释放其独立Skeleton boneTexture，不销毁借用的几何/材质/纹理；后者仍可能供战斗使用。细节替换保留用户拖动方向，重新取景时刷新真实face_focus世界坐标。生产模块没有测试调试全局；浏览器证据使用HTTP route注入，只读取冻结文件。

制作顺序为原人体/服装/动作生成→完整source rig保存→真实PBR atlas烘焙、骨骼转权重与两级减面→GLB/来源/权重/预算/动作检查→原生近景/战斗/交互验收。每阶段证据与运行模型分开；原模离线Cycles画面不代替最终GLB游戏镜头。
